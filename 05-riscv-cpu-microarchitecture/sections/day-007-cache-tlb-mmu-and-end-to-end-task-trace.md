# Day 7 — Cache, TLB, MMU, and End-to-End Task Trace

**Target time:** approximately 2½–3 hours

- Core-to-cache requests, hits, misses, and stalls: 40 minutes
- TLB translation, page-table walks, and permission checks: 45 minutes
- Runnable observation model: 40 minutes
- C `sum` trace from source to transistor switching: 45 minutes
- Mastery evidence and systems bridge: 20 minutes

> The core has decoded a load from virtual address `0x4004`. Why can it not
> simply read that address from RAM and continue on the next clock?

Three independent questions must be answered:

1. **Translation:** which physical address, if any, corresponds to this
   virtual address?
2. **Permission:** may this access execute, read, or write at the current
   privilege level?
3. **Data availability:** does the relevant cache already hold the physical
   line, or must the request wait for a lower level?

A TLB helps answer the first two questions quickly. A cache helps answer the
third. A TLB miss is not a cache miss, and neither event is automatically a
fault.

Today ends the CPU-design module by tracing a small task through every layer:

```text
C source
  → compiler-selected RISC-V instructions
  → architectural effects
  → fetch/decode/datapath activity
  → cache and TLB behavior
  → OS-created page-table policy
  → gates, wires, and state elements
  → transistor conduction and charge movement
```

---

## 1. Four layers, four kinds of statement

The most important discipline is to label each claim.

### Architectural layer: the software-visible contract

For this lesson, architectural facts include:

- the meanings of RISC-V instructions such as `lw`, `add`, `addi`, and
  `bne`;
- the values eventually visible in integer registers;
- the virtual address generated by a load or instruction fetch;
- whether an access completes or raises an architectural exception;
- the required ordering behavior of memory operations.

The ISA does not require a particular cache size, TLB replacement rule,
pipeline depth, or transistor arrangement.

### Microarchitectural layer: how this core implements the contract

Implementation choices include:

- separate L1 instruction and data caches;
- direct-mapped versus set-associative caches;
- whether cache lookup overlaps address translation;
- TLB size and replacement;
- a hardware page-table walker;
- request/response handshakes, miss-status state, and pipeline stalls;
- coherence protocol and ordering machinery.

Two compliant cores may choose differently and still run the same binary.

### OS-policy layer: what mappings and permissions should exist

The operating system:

- allocates physical page frames;
- creates and changes page-table entries;
- assigns user/supervisor and read/write/execute permissions;
- chooses address-space identifiers and mappings;
- handles page-fault exceptions;
- decides whether to allocate, load, kill, signal, or resume a task.

Hardware enforces encoded permissions. It does not decide that a C array
“deserves” another page.

### Physical layer: how bits actually change

At the physical layer:

- voltage ranges represent bits;
- transistor gates control conductive paths;
- capacitances charge or discharge;
- combinational paths settle after finite delay;
- clocked state captures values subject to setup/hold constraints;
- switching consumes energy and produces heat.

“The TLB compares a tag” is a microarchitectural statement. Physically, that
comparison is a large network of switching devices and wires.

## 2. Connecting the core to instruction and data caches

A simple core can expose two logical request paths:

```text
fetch unit                                   load/store unit
──────────                                   ───────────────
instruction virtual address                 data virtual address
        │                                            │
        ▼                                            ▼
  translation/check                            translation/check
        │ physical address                           │ physical address
        ▼                                            ▼
   instruction cache                              data cache
        │ instruction word                           │ load data / store ack
        └──────────────► core ◄──────────────────────┘
```

Separate paths permit an instruction fetch and data access to proceed
together. A unified cache is also possible. Neither organization is mandated
by the ISA.

### A request needs backpressure

The core cannot assume every access finishes immediately. A useful conceptual
interface is:

```text
request:  valid, address, operation, size, write_data
response: ready, read_data, fault
```

On a hit, `ready` may return quickly. On a miss, the cache records enough
information to request the line from the next level. The pipeline stage
holding the dependent instruction must wait, or another mechanism must track
the outstanding work.

For a small in-order core:

```text
data-cache hit
  → load obtains bytes
  → extension/writeback proceeds

data-cache miss
  → load cannot retire yet
  → freeze dependent pipeline state
  → request line from lower level
  → fill cache
  → replay or complete load
  → resume
```

A **stall** changes when progress occurs, not what the instruction means.
The implementation must hold or explicitly invalidate each affected state
element. Merely “pausing the PC” while later stages continue to overwrite
pipeline registers corrupts instruction ownership.

### Instruction misses also stall progress

If the instruction cache misses, no valid instruction word exists for that
PC yet. A small core can hold the fetch PC and inject no new instruction
until the line arrives. Older instructions already in the pipeline may still
finish if the design permits it.

Real cores can sustain several misses, speculate, prefetch, execute unrelated
instructions, and retire in order. Those optimizations enlarge the tracking
problem; they do not remove the need to preserve precise architectural
behavior.

## 3. A tiny direct-mapped cache model

Use a deliberately small cache:

```text
line size = 16 bytes
sets      = 4
ways      = 1
capacity  = 64 bytes
```

For physical address `PA`:

```text
line_number = PA // 16
offset      = PA % 16
set         = line_number % 4
tag         = line_number // 4
```

Each set stores a valid bit, tag, and sixteen data bytes. On lookup:

1. select one set;
2. compare its stored tag while checking valid;
3. on a match, select bytes by offset;
4. otherwise fetch the aligned physical line and replace that set.

The model below charges one cycle for a hit and eight extra cycles for a
fill. Those numbers are teaching parameters, not claims about RISC-V or real
silicon.

### Why caches normally use physical identity

Virtual aliases can map different virtual addresses to the same physical
page. If a cache treated those aliases as unrelated storage, the core could
hold inconsistent copies of one physical location. Practical designs use
physical tags or carefully constrained virtual indexing and OS cooperation.

The exact point at which translation and cache lookup overlap is
microarchitectural. Keep the correctness model simple:

```text
virtual request → translate/check → physical cache lookup
```

## 4. Translation: page offset stays, page identity changes

Assume 4 KiB pages:

```text
virtual address
┌──────────────── virtual page number ────────────────┬─ page offset ─┐
│                       VPN                            │    12 bits     │
└──────────────────────────────────────────────────────┴────────────────┘
```

A valid page-table entry supplies a physical page number:

```text
physical address = (PPN << 12) | page_offset
```

Translation changes the page identity, not the offset within that page.

### What the TLB caches

A translation lookaside buffer caches recently used translation metadata:

```text
(address-space identity, virtual page number)
    → physical page number + permission/state attributes
```

It does not cache the array element's value. That is the data cache's job.
It also must not confuse identical virtual addresses belonging to different
process address spaces; an ASID or TLB invalidation strategy handles that
distinction.

### TLB hit

On a matching valid TLB entry:

1. retrieve PPN and permission attributes;
2. check the requested access and privilege;
3. form the physical address;
4. continue toward the cache.

### TLB miss

A TLB miss means only:

> The fast translation cache lacks the needed translation.

On systems with a hardware page-table walker, the MMU reads page-table
structures from memory. Those reads can themselves interact with caches.
If the walk finds a valid permitted leaf entry, the hardware can fill the TLB
and retry the original access.

```text
TLB miss
  → walker locates root selected for this address space
  → reads page-table entry at each required level
  → validates leaf and permissions
  → fills TLB
  → retries original access
```

The full RISC-V Sv32/Sv39 algorithms include levels, PTE formats, superpages,
accessed/dirty state, and precise fault conditions. The lab compresses these
details into a dictionary lookup so the responsibility boundary remains
visible. It is not an Sv39 emulator.

### Page-table memory is ordinary memory with an extraordinary role

A page table is a data structure in memory created by privileged software.
The CPU is told where its root is and interprets entries according to the
architecture. A hardware walk therefore creates extra memory traffic:

```text
one requested load
  → zero page-table reads on a TLB hit
  → several possible page-table reads on a TLB miss
  → then the requested data-cache access
```

This is why TLB reach and page-walk locality affect system performance.

## 5. Missing, invalid, and denied are not the same

Suppose a walk reaches one of these simplified entries:

```text
VPN 0x4 → PPN 0x20, user, readable, not writable, not executable
VPN 0x1 → PPN 0x10, user, executable, readable
VPN 0x9 → no valid entry
```

Results:

- user instruction fetch from VPN `0x1`: translation can succeed;
- user load from VPN `0x4`: translation can succeed;
- user store to VPN `0x4`: permission fault;
- access to VPN `0x9`: not-present/invalid translation fault.

A cache hit cannot override a permission failure. Permission checking belongs
to translation/protection and must occur even if physical data remains in a
cache from earlier use.

### Fault mechanism versus OS response

The hardware:

1. detects that the architectural access cannot complete;
2. records a cause and faulting virtual address;
3. preserves a precise restart point according to the ISA;
4. transfers control to a privileged trap handler.

The OS then applies policy:

- map a page and resume for a legitimate demand fault;
- update bookkeeping and resume where architecture permits;
- reject an illegal access and terminate or signal the process;
- emulate or otherwise handle a special mapping.

“The MMU kills the process” is wrong. The MMU reports an architectural fault;
the OS decides the task-level response.

## 6. Ordering and coherence: boundary map only

Today needs two definitions, not a complete protocol or memory-model course.

### Memory ordering

Memory ordering specifies which observations of loads, stores, and explicit
ordering operations software may rely on. A core may buffer, overlap, or
reorder internal memory work, but it must obey the architecture's ordering
rules. RISC-V has a relatively weak memory model and provides mechanisms such
as `FENCE`; language atomics and synchronization libraries compile to the
required instruction sequences.

A cache hit does not by itself prove that all cores may observe earlier
stores in source order.

### Cache coherence

Coherence coordinates copies of the same physical cache line among agents so
writes and ownership are handled consistently. It operates on physical memory
identity and commonly at cache-line granularity. Coherence does not replace:

- page-table permissions;
- the architectural memory-ordering model;
- C's data-race and atomic rules;
- OS synchronization policy.

For this tiny single-core observation model, coherence is intentionally out
of scope. The model has only one cache hierarchy and no second observer.

### Architecture comparison — memory systems, privilege, and virtualization

Across x86-64, AArch64, and RISC-V, cache and TLB capacities, associativity,
replacement, split/unified organization, and walk-cache design are
**microarchitectural**. The **architecture** instead defines translation
formats, permissions, faults, maintenance operations, privilege state, and
memory-ordering guarantees:

- x86-64 commonly uses `CR3`-rooted multilevel tables, 4 KiB base pages and
  larger pages; supported address widths and level counts are feature
  dependent. Privilege is expressed through CPL/rings and page permissions.
  VMX/SVM systems can add EPT/NPT second-level translation.
- AArch64 uses translation regimes selected through system registers, with
  architected 4 KiB, 16 KiB, and 64 KiB granules. EL0–EL3 describe exception
  levels; EL2 and stage-2 translation support virtualization.
- RISC-V selects a supported scheme through `satp`: RV32 commonly uses Sv32,
  while RV64 systems may implement Sv39, Sv48, or Sv57. U/S/M modes define
  privilege; the optional hypervisor extension adds HS/VS/VU state and
  two-stage translation.

Page-table entry layouts, fault reports, invalidation instructions, and
virtualization control state therefore differ. All three still need
translation caching, permission checks, precise faults, and synchronization
after mapping changes. Their ordering contracts also differ: x86-64 is
relatively strong and TSO-style, while AArch64 and RISC-V RVWMO permit weaker
ordering with explicit acquire/release and barrier/fence mechanisms.

The **OS or hypervisor policy** remains distinct: software allocates page
tables, chooses mappings and permissions, handles faults, performs required
TLB maintenance, and decides whether a guest or task resumes. Linux and KVM
provide common abstractions, but architecture-specific code supplies these
mechanisms. See
[Architecture Comparison for Systems Programmers](../../references/ARCHITECTURE_COMPARISON.md).

## 7. Runnable safe observation lab

This lab models:

- 4 KiB virtual pages;
- a four-entry fully associative TLB;
- an OS-supplied page-table dictionary;
- translation and permission checks;
- separate tiny direct-mapped instruction and data caches;
- explicit cycle charges for hits, cache fills, and page-table walks.

It reads no privileged state, changes no system mappings, requires only
Python 3, and writes nothing. Run from any directory:

```bash
python3 - <<'PY'
from dataclasses import dataclass

PAGE = 4096
LINE = 16
SETS = 4

@dataclass(frozen=True)
class PTE:
    ppn: int
    user: bool
    read: bool
    write: bool
    execute: bool

PAGE_TABLE = {
    0x1: PTE(0x10, True, True,  False, True),   # code: VA 0x1000
    0x4: PTE(0x20, True, True,  False, False),  # array: VA 0x4000
    0x7: PTE(0x30, True, True,  True,  False),  # writable data
}

class TLB:
    def __init__(self, capacity=4):
        self.capacity = capacity
        self.entries = {}
        self.order = []

    def translate(self, va, access):
        vpn, offset = divmod(va, PAGE)
        if vpn in self.entries:
            pte = self.entries[vpn]
            print(f"  [microarchitecture] TLB HIT  vpn=0x{vpn:x}")
            cycles = 1
        else:
            print(f"  [microarchitecture] TLB MISS vpn=0x{vpn:x}")
            print("  [microarchitecture] hardware page-table walk")
            pte = PAGE_TABLE.get(vpn)
            cycles = 6
            if pte is None:
                raise PermissionError(
                    f"[architecture] page fault: no valid PTE for VA 0x{va:x}"
                )
            if len(self.order) == self.capacity:
                victim = self.order.pop(0)
                del self.entries[victim]
            self.entries[vpn] = pte
            self.order.append(vpn)
            print(
                f"  [OS policy data] PTE vpn=0x{vpn:x} -> ppn=0x{pte.ppn:x}"
            )

        allowed = {
            "fetch": pte.execute,
            "load": pte.read,
            "store": pte.write,
        }[access]
        if not pte.user or not allowed:
            raise PermissionError(
                f"[architecture] {access} page fault at VA 0x{va:x}"
            )
        return pte.ppn * PAGE + offset, cycles

class DirectCache:
    def __init__(self, name):
        self.name = name
        self.lines = [None] * SETS

    def access(self, pa):
        line_number = pa // LINE
        index = line_number % SETS
        tag = line_number // SETS
        hit = self.lines[index] == tag
        event = "HIT " if hit else "MISS"
        print(
            f"  [microarchitecture] {self.name} {event} "
            f"pa=0x{pa:x} set={index} tag=0x{tag:x}"
        )
        if not hit:
            self.lines[index] = tag
        return 1 if hit else 9

tlb = TLB()
icache = DirectCache("I-cache")
dcache = DirectCache("D-cache")
cycles = 0

def request(kind, va):
    global cycles
    print(f"\n[architecture] {kind} VA 0x{va:x}")
    try:
        pa, cost = tlb.translate(va, kind)
        print(f"  [architecture] translated PA 0x{pa:x}")
        cost += (icache if kind == "fetch" else dcache).access(pa)
        cycles += cost
        print(f"  [microarchitecture] request completes; +{cost} cycles")
    except PermissionError as fault:
        cycles += 6
        print(f"  {fault}")
        print("  [OS policy] trap handler decides whether task may resume")

for kind, va in [
    ("fetch", 0x1000),  # TLB miss, I-cache miss
    ("fetch", 0x1004),  # TLB hit, same I-cache line hit
    ("load",  0x4000),  # TLB miss, D-cache miss
    ("load",  0x4004),  # TLB hit, same D-cache line hit
    ("store", 0x4004),  # TLB hit, denied by read-only PTE
    ("load",  0x9000),  # TLB miss, no valid PTE
]:
    request(kind, va)

print(f"\n[observation] modeled total = {cycles} cycles")
print("[limit] timing and policies are teaching parameters, not a real CPU")
PY
```

### Predict before running

For each request, write:

1. VPN and page offset;
2. whether the TLB should hit;
3. whether translation is permitted;
4. physical address when permitted;
5. cache set and expected hit/miss;
6. whether control returns normally or enters the trap path.

### Explain after running

Account for these distinct events:

- The first fetch misses in both the TLB and I-cache.
- The second fetch hits in the TLB and the same 16-byte cache line.
- The first array load requires a walk and a D-cache fill.
- The second array load uses both cached translation and cached data line.
- The store faults even though the D-cache has the line.
- The final load faults because no valid mapping exists.

Then change only one item:

- grant write permission to VPN `0x4`;
- move the second load to `0x4010`, the next cache line;
- reduce TLB capacity to one;
- add a valid PTE for VPN `0x9`.

Predict which layer's events change. Do not describe a permission change as a
cache optimization or a cache-line change as OS policy.

### What this lab cannot prove

It is not cycle-accurate and does not implement:

- the full RISC-V privileged architecture or Sv32/Sv39 PTE format;
- multilevel page-table address calculation;
- real cache data bytes, dirty writeback, or nonblocking misses;
- accessed/dirty-bit rules, superpages, ASIDs, or TLB shootdowns;
- speculation, prefetching, coherence, or the RISC-V memory model;
- physical timing, power, analog behavior, or transistor count.

Its evidence is narrower: the event ordering and layer boundaries are
explicit and mechanically repeatable.

## 8. Compile a tiny `sum` into architectural work

Use:

```c
int sum(const int *a, int n) {
    int s = 0;
    for (int i = 0; i < n; ++i)
        s += a[i];
    return s;
}
```

A compiler targeting RV32I might choose a loop conceptually like this:

```asm
# a0 = pointer a, a1 = n, return value in a0
sum:
    addi t0, x0, 0       # s = 0
loop:
    bge  x0, a1, done    # if n <= 0, finish
    lw   t1, 0(a0)       # load *a
    add  t0, t0, t1      # s += *a
    addi a0, a0, 4       # a++
    addi a1, a1, -1      # n--
    jal  x0, loop
done:
    addi a0, t0, 0       # return s
    jalr x0, 0(ra)
```

This is illustrative, not a promise of exact compiler output. Optimization
level, extensions, ABI assumptions, alignment knowledge, unrolling, and
vector support can produce different legal sequences. The C abstract machine
defines behavior; the compiler chooses instructions that preserve that
behavior under its assumptions. The concrete trace assumes `a` designates at
least `n` valid `int` objects and the mathematical sum is representable as an
`int`; otherwise the C source itself may have undefined behavior.

### One iteration, layer by layer

Assume `a0 = 0x4000`, `a1 = 2`, and memory contains `7, 11`.

#### 1. Architectural view

For `lw t1, 0(a0)`:

```text
effective virtual address = x[a0] + sign_extend(0) = 0x4000
architectural result      = x[t1] receives the loaded 32-bit value
```

If translation or permission fails, the register write must not commit.

#### 2. Fetch microarchitecture

The fetch unit presents the instruction PC as a virtual address. The
instruction TLB translates it; the I-cache supplies the instruction word or
stalls fetch during a fill. The PC and pipeline-valid state are held or
redirected according to the design.

#### 3. Decode microarchitecture

Decoder logic recognizes the `lw` opcode and fields. It selects:

- register `a0` as source;
- an I-type immediate of zero;
- addition in the address-generation ALU;
- a four-byte load;
- writeback to `t1`;
- no store and no branch redirect.

These control wires are not architectural registers. They are one
implementation's way of producing the required effect.

#### 4. Datapath and translation

The register file drives `0x4000`. The immediate network drives zero. Operand
muxes select them, and the adder settles to virtual address `0x4000`.

The data TLB either supplies the PPN and permissions or triggers a page-table
walk. The PTE exists because the OS mapped the process's array page. If it is
valid, user-readable, and sufficiently aligned for the architecture's rules,
the MMU forms the physical address.

#### 5. Data cache and stall

On a D-cache hit, the selected bytes proceed toward load-data alignment and
writeback. On a miss:

```text
hold the load and its destination identity
  → request the physical line
  → wait
  → fill
  → obtain the four bytes
  → write t1 only when the instruction completes
```

The ISA-visible result is still `t1 = 7`; only elapsed cycles differ.

#### 6. Dependent addition

`add t0, t0, t1` depends on the load. If data returns late, forwarding cannot
invent it. An in-order pipeline stalls until the value exists, then operand
muxes select the old sum and loaded value. The ALU computes the new sum.

After two iterations:

```text
t0 = 18
a0 = 0x4008
a1 = 0
```

The branch reaches `done`, and ABI-selected register `a0` receives 18.

## 9. Continue below RTL: gates and transistor switching

Choose one bit slice of the address addition or sum addition.

At the logical level, a full-adder relation is:

```text
sum_i   = A_i XOR B_i XOR carry_i
carry_o = (A_i AND B_i) OR (carry_i AND (A_i XOR B_i))
```

The physical story is:

1. register output nodes hold voltage ranges representing operand bits;
2. decode and select signals drive mux gate inputs;
3. transistor networks in those muxes establish conductive pull-up or
   pull-down paths;
4. effective node capacitances charge or discharge;
5. changed voltage ranges propagate through the adder's gate network;
6. carry and sum nodes settle after finite delay;
7. a destination state element samples its input at an allowed clock edge;
8. clock distribution and state-element switching consume energy even when
   the architectural instruction name says only `add`.

Do not claim that one C `+` maps permanently to one physical adder. The
compiler may transform the loop; the microarchitecture may share, pipeline,
or duplicate arithmetic; synthesis may rewrite the gate network; physical
implementation chooses concrete cells and wires.

### The complete trace

```text
C: s += a[i]
│
├─ language/compiler layer
│    defined C values and compiler-selected lw/add instructions
│
├─ architectural layer
│    PC, registers, virtual load address, result, possible exception
│
├─ microarchitectural layer
│    fetch/decode, register read, ALU, pipeline state, I/D cache, TLB,
│    page-table walker, stalls, fills, forwarding, writeback
│
├─ OS-policy layer
│    page-table root, VA→PA mapping, user/read/write/execute permissions,
│    fault-handler decision
│
└─ physical layer
     voltage ranges, transistor conduction, capacitance, delay, clocked
     capture, switching energy
```

The causal chain runs downward to physics and back upward through committed
architectural state. No layer makes the others unnecessary.

## 10. Systems consequences

### Context switches and translation state

When the OS switches address spaces, the same virtual address may mean a
different physical page. The kernel and architecture coordinate through a
page-table-root register, ASIDs where available, and required invalidation or
fencing operations. Stale translations are a correctness and isolation
problem, not merely a performance problem.

### Changing a PTE is not enough by itself

A translation may already be cached in a TLB. After changing page tables, the
OS follows architecture-defined synchronization steps so later accesses do
not keep using forbidden stale metadata. On multiple CPUs, this can require
remote TLB invalidation—often called a TLB shootdown.

### Page faults must be precise enough to resume

A demand-paged array can initially have no resident physical frame. The load
faults; the kernel validates the virtual mapping, allocates or retrieves a
page, updates page tables, performs required synchronization, and returns.
The architectural load can then be retried. The cache and pipeline must not
have committed the denied/incomplete load as if it succeeded.

### Device memory is a different future path

Drivers may map device registers with cacheability and ordering attributes
different from ordinary RAM. Using a normal cached-load mental model for MMIO
can be incorrect. Later ToyOS and driver work will add memory types, barriers,
interrupts, DMA, and IOMMU behavior deliberately.

## Final bridge to ToyOS

The core now has the mechanisms an operating system expects:

```text
architectural state + privilege + precise traps
  + address translation + permission enforcement
  + interruptible, stallable memory access
```

ToyOS will supply the policy:

```text
boot
  → install exception entry
  → allocate physical pages
  → construct page tables
  → map kernel and user addresses
  → handle faults
  → schedule task state
  → enter user mode and service system calls
```

The same four-layer discipline continues. RISC-V or x86-64 defines visible
mechanisms; the CPU implements them; the kernel configures and responds to
them; gates and transistors make every state transition physical.
